# Detect first, then generate: 2026's moving targets

The 2026 React + Next.js stack has a clear set of dominant conventions, but **five upstream changes in the last ten months invalidate templates written against 2024–25 defaults**, and a generator can only encode them deterministically if it detects the project's choices before rendering. The changes are: shadcn made **Base UI the default primitive library in July 2026** (`render` prop instead of `asChild`); shadcn moved `cn` into **its own `cn` package in September 2026**; **Next.js 16** renamed `middleware.ts` to `proxy.ts`, removed synchronous `params`/`searchParams`/`cookies()`, and made `default.js` mandatory for parallel-route slots; **TanStack Table v9** (stable August 2026) replaced `useReactTable` and the `get*RowModel` options; and **Zod 4** is now the root `"zod"` export with a reworked API that even the official Next.js forms guide still gets wrong. The dominant conventions are steady underneath the churn. Use a feature-folder layout with direct imports and no barrels. Write `type` aliases and `as const` objects instead of enums, and derive types from Zod schemas. On the server, use a `server-only` Data Access Layer and Server Actions. On the client, use React Query `queryOptions` factories. Add Zustand only when cross-tree client state truly exists, and prefer nuqs for URL state. Auth runs through a library (Better Auth by default), and every action re-checks it. For a codegen skill that currently pins Radix Slot and finds `cn()` through `components.json` aliases, the practical implication is a single detection pass. That pass reads `package.json` majors, the `components.json` `style` prefix, and the existing file layout, and selects a template variant per topic.

## Five upstream shifts break the current generator's assumptions

The highest-impact change is in shadcn. **New projects now use Base UI by default; `npx shadcn init` selects it, Radix "is not being deprecated", and `-b radix` keeps the old behaviour** ([shadcn changelog](https://ui.shadcn.com/docs/changelog/2026-07-base-ui-default)). shadcn's own migration note says "`asChild` is now `render`", and its docs now show triggers as `<AlertDialogTrigger render={<Button variant="outline" />}>` ([shadcn AlertDialog](https://ui.shadcn.com/docs/components/alert-dialog)). `components.json` has **no separate "base library" key**. The primitive library is encoded in the `style` value: `radix-*`, `base-*` or `aria-*` crossed with `vega|nova|maia|lyra|mira|luma|sera|rhea`, alongside the legacy `default` and `new-york` ([shadcn schema.json](https://ui.shadcn.com/schema.json)). The generator today decides polymorphism from whether `@radix-ui/react-slot` or `radix-ui` is in `package.json` (`scripts/lib/detect.mjs`, `detectSlot`). In a fresh Base UI project neither package is present, so the component template either falls back to no polymorphism or, worse, adds a Radix dependency the project never chose. The fix is to read `style` first and branch: `radix-*`/`new-york`/`default` keep `Slot`/`Slot.Root` + `asChild`, while `base-*` emits a `render` prop. The `aria-*` (React Aria) flavor's trigger composition was not verified and should get no polymorphic prop until it is checked.

The same changelog records that **`cn` is imported from the `cn` package in every component as of September 2026** ([shadcn changelog](https://ui.shadcn.com/docs/changelog)). It also records May 2026 "package imports/target aliases" support. `detectCn` returns `aliases.utils` or falls back to a regex over `lib/utils.ts`. In a project generated after September, that path can point at a file that no longer exports `cn`, or at nothing at all. The robust rule is to import `cn` the way the project's existing `components/ui/*` files do, and use the alias logic only as a fallback when no UI components exist yet. The research did not capture the exact shape of the new `cn` package import or of the package-import aliases, so verify both against a freshly initialized project before encoding them.

Next.js 16 changes three things the Next pack touches. **"Synchronous access is fully removed" for `params`, `searchParams`, `cookies()`, `headers()` and `draftMode()`**. **"All parallel route slots now require explicit `default.js` files. Builds will fail without them."** And **the `middleware` file is deprecated in favour of `proxy`**, which runs only on the Node.js runtime ([Next.js 16 upgrade guide](https://nextjs.org/docs/app/guides/upgrading/version-16); [proxy.js reference](https://nextjs.org/docs/app/api-reference/file-conventions/proxy)). The generator's page template already branches on `asyncParams`, which is correct. Any future auth, modal or dashboard template must also branch on the `next` major for the proxy filename and export name, and always emit `default.tsx` beside every `@slot`. Using the wrong filename fails silently. Supabase warns that on Next 15 and earlier "a `proxy.ts` file is never called, so sessions never refresh" ([Supabase SSR guide](https://supabase.com/docs/guides/auth/server-side/nextjs)). Cache Components (`cacheComponents: true`) is on by default in new `create-next-app` apps ([Next.js Caching](https://nextjs.org/docs/app/getting-started/caching)). It turns unwrapped runtime access such as `cookies()` in a layout into a build-time error ([Next.js layout.js](https://nextjs.org/docs/app/api-reference/file-conventions/layout)), so templates that read request data must wrap that read in `<Suspense>`.

The remaining two shifts are in libraries. **TanStack Table v9 renames `useReactTable` to `useTable`, makes `features` a required option declared via `tableFeatures()`, and moves row models into feature slots** (`sortedRowModel: createSortedRowModel()`). Types gain a leading `TFeatures` generic (`ColumnDef<TFeatures, TData, TValue>`), and `useLegacyTable` is "deprecated and intended only as a temporary migration aid" ([TanStack v9 migration](https://tanstack.com/table/v9/docs/framework/react/guide/migrating.md); [announcement](https://tanstack.com/blog/announcing-tanstack-table-v9)). **Zod 4 has been the `"zod"` root export since July 2025**. It replaces `message` with `error`, `z.string().email()` with `z.email()`, `z.nativeEnum` with `z.enum`, and `.strict()`/`.passthrough()` with `z.strictObject()`/`z.looseObject()`. It requires two arguments for `z.record`, and its `.default()` now short-circuits on `undefined` ([Zod versioning](https://zod.dev/v4/versioning); [Zod v4 changelog](https://zod.dev/v4/changelog)). The Next.js Forms guide, updated October 2026, still uses `invalid_type_error` and `.flatten()` ([Next.js Forms guide](https://nextjs.org/docs/app/guides/forms)). Copying official snippets verbatim therefore produces deprecated code.

| Assumption in a 2024–25 generator | 2026 reality | Detection signal |
|---|---|---|
| shadcn = Radix, polymorphism via `Slot` + `asChild` | Base UI default, `render` prop; Radix opt-in | `components.json` `style` prefix |
| `cn` lives in `@/lib/utils` | `cn` package since Sept 2026 | imports in existing `components/ui/*` |
| `middleware.ts` | `proxy.ts` (Next ≥16), Node runtime only | `next` major |
| `params` may be sync; slots optional `default` | async only; `default.tsx` required | `next` major |
| `useReactTable` + `get*RowModel()` | `useTable` + `tableFeatures()` | `@tanstack/react-table` major |
| `z.string().email()`, `message`, `nativeEnum` | `z.email()`, `error`, `z.enum` | `zod` major (`3.25.x` may use `"zod/v4"`) |
| vaul-based Drawer, `direction="bottom"` | Base UI Drawer, `swipeDirection="down"` | `vaul` in deps / `style` prefix |
| `h-4 w-4` on icons | `size-*` (parent matches `class*='size-'`) | none needed; always emit `size-*` |

One more mismatch sits in the existing pack. `server-action/action.ts.tpl` exports `action(formData)`, but the dominant form pattern binds actions to `useActionState`, which calls them as `(prevState, formData)`. That is the shape of the Next.js docs' `signup(state: FormState, formData: FormData)` used with `const [state, action, pending] = useActionState(signup, undefined)` ([Next.js Authentication guide](https://nextjs.org/docs/app/guides/authentication)). A template meant for forms should emit the two-argument signature.

## Feature folders, derived types and one shared schema form the stable core

Next.js itself is "unopinionated" about organization. It offers `src/`, `_private` folders and `(group)` route groups, and its only firm advice is to "choose a strategy… and be consistent" ([Next.js Project Structure](https://nextjs.org/docs/app/getting-started/project-structure)). The de facto convention fills that gap: **bulletproof-react's `src/features/<name>/{api,components,hooks,stores,types,utils}` plus shared top-level `components/ hooks/ lib/ types/ utils/ config/`**. Imports flow one way (shared → features → app), and cross-feature imports are banned with `import/no-restricted-paths` ([bulletproof-react](https://github.com/alan2207/bulletproof-react/blob/master/docs/project-structure.md)). Barrels have fallen out of favour. bulletproof-react now recommends direct imports, and TkDodo measured a Next.js project going from more than 11k to about 3.5k modules after removing internal barrels ([TkDodo](https://tkdodo.eu/blog/please-stop-using-barrel-files)). The generator should therefore create no `index.ts` files by default. It should still append to a barrel that already exists, which it already does. Detection is cheap. If `src/app` exists, the root is `src/`. A `features/` directory signals a feature layout, and `app/**/_components` signals route-colocation. The "promote to shared when a second feature needs it" rule is an inference from the no-cross-imports rule, not a sourced threshold.

On types, **authorities split on `type` vs `interface`**. typescript-eslint's stylistic config defaults to `interface` ([typescript-eslint](https://typescript-eslint.io/rules/consistent-type-definitions/)), while Matt Pocock recommends "`type` by default" and `interface` only for inheritance ([Total TypeScript](https://www.totaltypescript.com/type-vs-interface-which-should-you-use)). The deterministic answer is to read the project's `consistent-type-definitions` setting and default to `type` when it is absent. Enums should never be generated. The TS handbook suggests `as const` objects instead ([TS Handbook](https://www.typescriptlang.org/docs/handbook/enums.html)), `erasableSyntaxOnly` makes enums errors ([Total TypeScript](https://www.totaltypescript.com/erasable-syntax-only)), and the npm `latest` TypeScript is now the 7.x native compiler line. Constants have no authoritative convention beyond bulletproof-react's `src/config` for env-backed config. Emit `export const X = {…} as const` (with `satisfies` when a shape must be enforced) and copy the project's casing.

Zod schemas should live next to their feature (`features/<f>/schemas.ts`, or `*.schema.ts` if that pattern exists), with types derived via `z.infer`/`z.input`. **The shared form/server schema must sit in a file with no `'use server'` or `'use client'` directive**, so the client form and the action can both import it. react-hook-form adds one trap here. A single generic `useForm<T>` conflicts with the resolver, so the generator should either omit generics or pass all three (`z.input`, context, `z.output`). Fields with `.default()` differ between input and output types ([@hookform/resolvers](https://github.com/react-hook-form/resolvers)). Server-side errors should go back as `z.flattenError(err).fieldErrors`, since `formatError` is deprecated ([Zod error formatting](https://zod.dev/error-formatting)). Env validation is conventionally `src/env.ts` with `@t3-oss/env-nextjs` `createEnv`, imported directly from `next.config.ts` on Next 16 ([t3-env](https://env.t3.gg/docs/nextjs)). If the project uses Valibot or ArkType instead, `standardSchemaResolver` keeps one code path through Standard Schema.

## Server-first data flow puts React Query and stores at the edges

Next.js's official guidance names three data approaches: an existing HTTP API, component-level access, and **a server-only Data Access Layer, "recommended for new projects"**. It tells teams to pick one and not mix them ([Next.js Data Security](https://nextjs.org/docs/app/guides/data-security)). The DAL files (`data/*.ts` with `import 'server-only'`) perform authorization and return minimal DTOs. Mutations go through thin `'use server'` actions that call the DAL and then `revalidatePath`/`revalidateTag`. For hand-written HTTP access, a thin native-`fetch` wrapper (`lib/api-client.ts`, bulletproof's pattern ([bulletproof api-layer](https://github.com/alan2207/bulletproof-react/blob/master/docs/api-layer.md))) beats axios. **Only native `fetch` receives Next's `cache`, `next.revalidate` and `next.tags` extensions** ([Next.js fetch reference](https://nextjs.org/docs/app/api-reference/functions/fetch)). axios, ky or ofetch should be reused only when they are already installed. When `@hey-api/openapi-ts`, `orval`, `openapi-fetch` or `@kubb/*` is present, the generator should not hand-write fetchers at all. hey-api already emits `<op>Options()` and `<op>Mutation()` for React Query ([hey-api plugin](https://heyapi.dev/openapi-ts/plugins/tanstack-query)). The `ApiError` class shape is community convention only.

For client fetching, **TanStack Query v5's dominant idiom is per-feature `queryOptions()` factories that co-locate key and `queryFn`**. TkDodo calls separating them "a mistake" and treats thin `useXxx` wrappers as optional ([TkDodo](https://tkdodo.eu/blog/the-query-options-api)). bulletproof-react instead uses one verb-first file per operation (`api/get-discussions.ts` exporting fetcher, `…QueryOptions` and `useDiscussions`) ([bulletproof](https://github.com/alan2207/bulletproof-react/blob/master/apps/nextjs-app/src/features/discussions/api/get-discussions.ts)). Both are legitimate, so the generator should match `features/*/api/get-*.ts` or `**/queries.ts` when either already exists. App Router wiring is prescribed by TanStack. It uses `get-query-client.ts`, which creates a new client per server request, keeps a browser singleton, sets `staleTime: 60_000`, and dehydrates pending queries. A `'use client'` provider wraps the app. Server Components call `void queryClient.prefetchQuery(opts)` inside `<HydrationBoundary>`, and clients call `useSuspenseQuery` ([TanStack Advanced SSR](https://tanstack.com/query/latest/docs/framework/react/guides/advanced-ssr)). Query options files therefore must not import `server-only`. v4-era names (`cacheTime`, `isLoading` for first load, `keepPreviousData: true`, `<Hydrate>`, query `onSuccess`) are outdated ([v5 migration](https://tanstack.com/query/latest/docs/framework/react/guides/migrating-to-v5)). The `mutationOptions()` helper was not verified and should not be emitted yet. Alternatives map cleanly. With SWR, use URL-string keys and `useSWRMutation`. With tRPC v11, use `useTRPC().x.queryOptions()` ([tRPC](https://trpc.io/docs/client/tanstack-react-query/usage)). With no client library, use a DAL plus Server Actions and `useActionState`.

Client stores should be opt-in. Zustand leads, with **40.9M weekly downloads against RTK's 21.9M** and React Query's 57.6M ([npm downloads API](https://api.npmjs.org/downloads/point/last-week/zustand)). Redux's own Next.js guide says to "use Redux only for globally shared, mutable data" ([redux.js.org](https://redux.js.org/usage/nextjs)). A generator should therefore route server data to React Query or RSC, URL state to nuqs, and local state to `useState`/context. It should emit a store only for cross-tree client state. In App Router, **module-level store singletons leak across concurrent requests**. Zustand's official layout is `stores/<name>-store.ts` (a `createStore` factory from `zustand/vanilla`) plus `providers/<name>-store-provider.tsx`, initialized with `useState(() => create…())`, not the older `useRef` ([Zustand Next.js guide](https://zustand.docs.pmnd.rs/learn/guides/nextjs)). RTK's equivalent is `lib/store.ts` `makeStore`, `lib/hooks.ts` with `.withTypes()`, and `app/StoreProvider.tsx`, again with `useState`. Jotai v3 (September 2026) is ESM-only and drops `atomFamily` from core ([InfoQ](https://www.infoq.com/news/2026/09/jotai-3-released/)), so v2 tutorials no longer apply. Zustand v5 removed the equality-function argument, so multi-field selectors need `useShallow` to avoid infinite loops ([Zustand v5 migration](https://zustand.docs.pmnd.rs/reference/migrations/migrating-to-v5)). A project that already has a store library must never get a second one.

## UI templates hinge on primitive flavor, row models and route segments

Icons follow `components.json`. Lucide is the default, but `iconLibrary` is a free-form string with no enum ([shadcn schema.json](https://ui.shadcn.com/schema.json)). Community sources list Tabler, HugeIcons, Phosphor and Remix as switchable options, each with different export naming (`Plus`, `IconPlus`, `RiAddLine`) ([shadcnstudio](https://shadcnstudio.com/blog/shadcn-icon-library/)). The generator therefore needs either a per-library name map or icon-free templates. Sizing is uniform across libraries. shadcn's Button applies `[&_svg:not([class*='size-'])]:size-4` ([shadcn button.tsx](https://raw.githubusercontent.com/shadcn-ui/ui/main/apps/v4/registry/new-york-v4/ui/button.tsx)), so icons inside primitives get no class, and overrides use `size-*`, never `h-4 w-4`. **Lucide icons ship `aria-hidden="true"` and the accessible name belongs on the button** ([Lucide accessibility](https://lucide.dev/guide/react/advanced/accessibility)), so icon-button templates should refuse to render without an `aria-label`. Next already applies `optimizePackageImports` to `lucide-react` and `@tabler/icons-react` by default, but Phosphor, HugeIcons and Remix are not on that default list ([Next.js optimizePackageImports](https://nextjs.org/docs/app/api-reference/config/next-config-js/optimizePackageImports)).

Each dialog type has a distinct job. Use AlertDialog for destructive confirmations, Dialog for forms, Sheet for side panels, and Drawer for mobile. **The Drawer now uses Base UI instead of vaul**, with `direction` renamed to `swipeDirection` and `asChild` to `render` ([shadcn Drawer](https://ui.shadcn.com/docs/components/drawer)). Form dialogs should be controlled (`open`/`onOpenChange`) so they can close after an async submit ([Radix Dialog](https://www.radix-ui.com/primitives/docs/components/dialog)). Templates should always render a Title, and on Radix should pass `aria-describedby={undefined}` when the Description is omitted. Base UI's `Dialog.createHandle()` supports detached triggers with typed payloads natively ([Base UI Dialog](https://base-ui.com/react/components/dialog)), which weakens the case for store-based "modal managers". Modals that need a shareable URL use a parallel `@modal` slot plus an intercepting `(.)segment` route, with `default.tsx` and a catch-all returning `null`, closed via `router.back()` ([Next.js Parallel Routes](https://nextjs.org/docs/app/api-reference/file-conventions/parallel-routes)). Interception prefixes count route segments while ignoring `@slot` and `(group)` folders ([Intercepting Routes](https://nextjs.org/docs/app/api-reference/file-conventions/intercepting-routes)), so the generator must compute depth the same way.

Tables have two tiers. Read-only lists use plain shadcn `Table` with a `TableCaption` and no TanStack. Interactive tables follow **shadcn's v9 layout: `data-table-features.ts`, client `columns.tsx` built with `createColumnHelper<DataTableFeatures, T>()`, generic client `data-table.tsx` using `useTable`, and an async server `page.tsx`** ([shadcn data-table.mdx](https://github.com/shadcn-ui/ui/blob/main/apps/v4/content/docs/components/radix/data-table.mdx)). Projects pinned to v8 keep a `useReactTable` variant, chosen by the installed major. Server-driven tables set `manual*` flags and keep state in nuqs search params. The parser object is shared between `createSearchParamsCache`/`createLoader` on the server ([nuqs](https://nuqs.dev/docs/server-side)) and the client, and tablecn (Next 16, Table 9, nuqs 2.10) is the reference implementation ([tablecn](https://github.com/sadmann7/tablecn)). The generator can cheaply improve on upstream in two ways. It can set `aria-sort` only on the sorted column ([APG sortable table](https://www.w3.org/WAI/ARIA/apg/patterns/table/examples/sortable-table/)), and it can size the empty-row `colSpan` to visible columns rather than `columns.length`. Virtualization should stay opt-in.

Layouts follow Next's file conventions. The root `app/layout.tsx` owns `<html>`/`<body>`, the Metadata API and one `'use client'` providers file. Section shells live in route-group layouts such as `(marketing)` and `(app)`. **Layouts cannot read `searchParams` or pathname and do not re-render on navigation** ([Next.js layout.js](https://nextjs.org/docs/app/api-reference/file-conventions/layout)), so active-link nav is a small client leaf. The shadcn app shell is `SidebarProvider > AppSidebar + SidebarInset`. `sidebar.tsx` still writes a `sidebar_state` cookie, but **the docs no longer show the cookie-reading layout** ([shadcn sidebar.tsx](https://github.com/shadcn-ui/ui/blob/main/apps/v4/registry/new-york-v4/ui/sidebar.tsx)). A generated persistence read is therefore a reconstruction, and it must sit in `<Suspense>` under Cache Components. For the plain-React pack, React Router's latest is **8.5.0** and imports come from `react-router`, with pathless layout routes rendering `<Outlet />` ([React Router](https://reactrouter.com/start/data/routing)).

## Auth templates must re-check inside every action and handler

Next.js's position is unambiguous. Use a library. Centralize checks in a `server-only` DAL (`verifySession`/`getCurrentUser` wrapped in React `cache`) that returns DTOs. **Re-verify inside every Server Action and Route Handler**, because "a page-level authentication check does not extend to the Server Actions defined within it" ([Next.js Data Security](https://nextjs.org/docs/app/guides/data-security)). Two caveats matter for codegen. First, **`cache` "does nothing" in Server Actions and Route Handlers** because they are not part of a render pass ([Next.js Authentication guide](https://nextjs.org/docs/app/guides/authentication)). Second, layouts are not a protection boundary, because they do not re-render and do not stop sibling content from rendering. `proxy.ts` is for optimistic, cookie-only redirects. CVE-2025-29927 let a client-supplied `x-middleware-subrequest` header skip middleware entirely on self-hosted deployments, and Vercel's lesson was not to use middleware "as the sole method of protecting routes" ([Vercel postmortem](https://vercel.com/blog/postmortem-on-next-js-middleware-bypass)). The current `action.ts.tpl` leaves auth as a TODO. That gap should become a rendered `await requireUser()` call against the detected library.

The library landscape has consolidated. **Auth.js was handed to the Better Auth team in September 2025**, and Better Auth is now "strongly recommended" for new projects ([Better Auth blog](https://www.better-auth.com/blog/authjs-joins-better-auth)). **Better Auth joined Vercel in July 2026** ([Better Auth blog](https://better-auth.com/blog/better-auth-joins-vercel)). `next-auth` v5 never left the npm `beta` tag, and `lucia` is deprecated. Each vendor has a native server read that the generator must call instead of decoding cookies itself:

| Detected dep | Server read / guard | Route mount | Proxy role |
|---|---|---|---|
| `@clerk/nextjs` | `await auth()` / `auth.protect({ role })` ([Clerk](https://clerk.com/docs/reference/nextjs/app-router/auth)) | none | required (`clerkMiddleware`) |
| `@supabase/ssr` | `(await createClient()).auth.getClaims()`; never `getSession()` server-side ([Supabase](https://supabase.com/docs/guides/auth/server-side/nextjs)) | none | required (session refresh) |
| `better-auth` | `auth.api.getSession({ headers: await headers() })`; `nextCookies()` last plugin ([Better Auth](https://www.better-auth.com/docs/integrations/next)) | `api/auth/[...all]` | optional |
| `next-auth` ≥5 | `await auth()` from `@/auth` ([Auth.js](https://authjs.dev/getting-started/installation?framework=next.js)) | `api/auth/[...nextauth]` | optional |
| `@kinde-oss/kinde-auth-nextjs` | `getKindeServerSession()` ([Kinde](https://docs.kinde.com/developer-tools/sdks/backend/nextjs-sdk/)) | `api/auth/[kindeAuth]` | route protection |
| `@workos-inc/authkit-nextjs` | `withAuth({ ensureSignedIn: true })` ([WorkOS](https://workos.com/docs/user-management/nextjs)) | `callback/route.ts` | route protection |
| none | hand-rolled `jose` session + `lib/dal.ts` `verifySession()` ([Next.js](https://nextjs.org/docs/app/guides/authentication)) | none | optional |

Authorization belongs next to the data. Templates should emit colocated predicates such as `canSeePhoneNumber(viewer, team)` in `server-only` DTO modules, ownership checks against IDOR in every mutation, 401/403 responses in handlers, and narrow client-component props rather than whole `User` objects ([Next.js Data Security](https://nextjs.org/docs/app/guides/data-security)). Clerk's `currentUser()` adds two specific hazards: it hits a rate-limited backend API on every call, and it carries `privateMetadata` ([Clerk](https://clerk.com/docs/reference/nextjs/app-router/current-user)). Wrapping any vendor in a local `lib/dal.ts` keeps vendor swaps contained, but that is a design inference, not vendor guidance.

## Conclusion

Most 2026 conventions are stable. What has changed is how fast their concrete syntax goes stale: the conventions persist, but the code that expresses them keeps changing. Four of the five breaking shifts landed after January 2026, and official docs themselves lag (the Next.js forms guide's Zod 3 code, the shadcn sidebar's missing cookie example, the shadcn reusable table components typed against the wrong features type). A generator that hard-codes any single snippet will drift within a quarter. The durable design is to treat every library-specific line as a variant keyed on a detected signal: the `components.json` `style` prefix, `package.json` majors for `next`, `zod`, `@tanstack/react-table`, `zustand`, `jotai` and `next-auth`, and the presence of existing `features/`, `queries.ts`, store or barrel files. A small fixture suite should pin each variant against a freshly initialized project. Teams starting with no shared convention should weigh one more point: for state and data, the strongest consensus position is to generate *less*. Use no store, no barrel and no custom query hook by default. Treat the server DAL plus Server Actions as the baseline that everything else is layered onto.

The open items to verify before encoding are the exact `cn` package import and May 2026 package-import aliases, React Aria trigger composition, the `mutationOptions` helper, RTK 2 `selectors`/`combineSlices`, and the Next "Authentication with Cache Components" rules. The research notes flagged each of these as unconfirmed.
